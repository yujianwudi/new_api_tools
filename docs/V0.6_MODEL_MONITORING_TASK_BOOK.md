# NewAPI Tools v0.6 模型可靠性监控任务书与验收标准

## 1. 文档目的

本文是 `new_api_tools` v0.6.0 模型监测完善工作的实施任务书、数据契约、验收标准和发行门禁。它用于约束开发、评审、测试、部署和回滚，不以“页面能打开”或“接口返回 200”作为完成标准。

参考项目 `WizisCool/model-status` 提供了主动探测、目录同步、首字延迟、公开状态页等有价值的设计，但 v0.6.0 不直接嵌入其 Node 服务，也不建立第二套控制面。核心能力在现有 Go 后端、React 前端和独立 Tool Store 中重新实现，并继续遵守 NewAPI Tools 的旁路边界。

## 2. 背景与问题

v0.5.2 的模型监测主要读取 NewAPI `logs` 表：

- 有真实请求时，可以根据 `type=2` 与 `type=5` 判断用户流量成功率；
- 没有真实请求时，只能显示无数据，不能证明模型当前是否可用；
- 原页面以大卡片、主题和排序配置为主，异常发现、错误原因和诊断下钻不够直接；
- 模型目录主要来自近期日志，刚上线或低流量模型可能无法进入监控范围；
- “可用性”“数据新鲜度”“主动探测结果”和“性能”没有形成统一、明确的状态契约。

v0.6.0 必须同时回答：

1. 真实用户是否正在受影响；
2. 没有真实流量时，模型接口是否仍然可用；
3. 状态证据是否新鲜、完整、可解释；
4. 主动探测是否受到成本、配额、并发和安全约束；
5. 运营人员能否在一个页面内发现异常、判断原因并查看最近证据。

## 3. 总目标

交付“模型可靠性控制台”，融合被动流量监测与主动合成探测，同时满足以下目标：

- 保留真实流量作为“用户影响”的权威证据；
- 使用默认关闭、白名单受控的主动探测补足无流量盲区；
- 不把性能慢等同于协议不可用；
- 不把无数据、过期数据或未适配模型显示成绿色；
- 不保存模型 API Key 或原始响应；
- 不修改 NewAPI schema，不进入模型代理主链路；
- 探测失败不能阻断 NewAPI、控制台登录或其他控制面功能；
- Dashboard 查询使用 Tool Store 聚合结果，不把全部历史明细读入应用内存；
- 认证后台优先展示异常，公开嵌入页保持兼容。

## 4. 不可破坏的边界

### 4.1 架构边界

- NewAPI Tools 仍是旁路控制面，不代理真实用户的模型请求。
- 主动探测只调用 `NEWAPI_BASEURL` 指向的 NewAPI 模型 API，不允许管理员通过 UI 配置任意上游 URL。
- NewAPI 主库和日志库保持只读；主动探测数据只写入 Tool Store。
- 主动探测默认关闭，缺少专用令牌或模型白名单时不得发送请求。
- `NEWAPI_ADMIN_ACCESS_TOKEN`、本工具 `API_KEY` 和 `MODEL_PROBE_API_KEY` 必须是三个独立信任边界，禁止自动回退或互相复用。

### 4.2 数据边界

- 不保存 API Key、请求 Authorization、原始响应正文、完整上游错误正文或用户数据。
- 只保存协议结果、语义结果、HTTP 状态、延迟、有限错误分类和响应 SHA-256。
- 错误信息最多 512 字节；错误代码最多 64 字节。
- 明细按保留策略删除，小时聚合按同一策略删除。
- 历史探测不能覆盖真实流量状态，真实流量也不能覆盖主动探测失败。

### 4.3 成本边界

- 模型必须进入精确白名单才能探测。
- 每次任务模型数量、并发、超时、输出 Token 和每日请求数均有硬上限。
- 图片、音频等高成本或未适配能力默认 `unsupported`，不得自动调用聊天端点。
- 日预算耗尽后调度和手动探测均失败关闭，不允许“先调用再记账”。
- 手动探测要求 `Idempotency-Key`，重复提交同一请求不得重复计费。

## 5. 版本范围

### 5.1 v0.6.0 必须交付

- 从 `abilities` 合并模型目录，使无流量模型仍可进入监控范围；
- 被动流量接口增加 `traffic_health`、`source_state` 和 `last_traffic_at`；
- 主动探测支持：
  - `/v1/chat/completions` 流式聊天；
  - `/v1/responses`；
  - `/v1/embeddings`；
  - `/v1/rerank`；
  - `unsupported` 安全跳过；
- Tool Store v9：探测任务、探测明细、小时聚合和保留清理；
- 单实例任务租约，计划任务和手动任务不能重叠；
- 进程启动时恢复遗留 `running` 任务，按已落库 attempt 重算计数并以 `process_restarted` 标记为 `cancelled`；
- 手动探测幂等、RBAC、请求体限制、白名单和日预算校验；
- 探测状态、历史和调度配置 API；
- 认证后台新版模型可靠性控制台；
- 异常优先列表、紧凑表格、移动端布局和右侧诊断抽屉；
- v0.6.0 配置、README、升级说明、回滚说明和发行门禁。

### 5.2 v0.6.0 明确不做

- 不直接合并或部署 `WizisCool/model-status` Node 服务；
- 不探测具体上游渠道，不强制指定 channel；
- 不自动切换渠道、封禁模型或修改 NewAPI 配置；
- 不主动生成图片、音频或视频；
- 不把公开嵌入页改成管理诊断页；
- 不提供任意提示词、请求体或 URL 的通用探测器；
- 不从模型输出中推断业务正确性或安全合规；
- 不把主动探测请求成本换算成货币金额；v0.6.0 只审计请求数量和限制参数；
- 不承诺多实例分布式任务租约；多实例部署需在后续版本引入数据库租约或专用调度器。

## 6. 状态契约

### 6.1 被动流量状态

每个模型返回：

```json
{
  "traffic_health": "healthy | degraded | unhealthy | unknown",
  "source_state": "fresh | stale | empty | unavailable",
  "last_traffic_at": 0,
  "success_rate": 99.5,
  "total_requests": 100
}
```

判定规则：

| 条件 | `traffic_health` | `source_state` |
|---|---|---|
| 成功率 ≥95%，且最近日志未过期 | `healthy` | `fresh` |
| 成功率 80%–95%，且最近日志未过期 | `degraded` | `fresh` |
| 成功率 <80%，且最近日志未过期 | `unhealthy` | `fresh` |
| 窗口内无请求 | `unknown` | `empty` |
| 有历史请求但最近日志超过 `LOG_FRESHNESS_MAX_SECONDS` | 保留统计值 | `stale` |
| 查询失败 | 不返回伪造结果 | `unavailable` 或接口明确失败 |

`type=2` 是成功消费记录，`type=5` 是明确失败；Embedding、Rerank 等合法的零 completion token 不得被额外算作失败。

### 6.2 主动探测状态

每个模型返回：

```json
{
  "probe_health": "healthy | degraded | unhealthy | stale | unavailable | pending | unsupported",
  "source_state": "fresh | stale | unavailable | pending | unsupported",
  "availability_24h": 100.0,
  "capability": "chat_completions",
  "reason_code": "ok",
  "reason": "最近主动探测成功"
}
```

判定规则：

| 条件 | `probe_health` |
|---|---|
| 最近探测成功且 24h 可用率 ≥95% | `healthy` |
| 最近探测成功但 24h 可用率 <95% | `degraded` |
| 最近探测失败 | `unhealthy` |
| 最近结果超过 `MODEL_PROBE_STALE_SECONDS` | `stale` |
| 系统正在运行但模型尚无结果 | `pending` |
| 能力为图片、音频或明确未适配 | `unsupported` |
| 未启用、未配置、非白名单或无数据 | `unavailable` |

### 6.3 综合状态

综合状态只用于 UI 排序与运营判断，不回写原始数据：

| 真实流量 | 主动探测 | 综合状态 |
|---|---|---|
| unhealthy | 任意 | 确认异常 |
| 任意 | unhealthy | 确认异常 |
| degraded/stale | 非 unhealthy | 需要关注 |
| 非 unhealthy | degraded/stale | 需要关注 |
| healthy | healthy | 双源健康 |
| healthy | unavailable/unsupported/unknown | 单源观测 |
| unknown/empty | healthy | 单源观测 |
| unknown/empty/stale | unavailable/unsupported | 证据不足 |

硬性规则：数据缺失、过期或查询失败不得显示“双源健康”。

## 7. 能力适配器

### 7.1 Chat Completions

- 端点：`POST /v1/chat/completions`
- 固定提示词：`Respond with exactly: ok`
- `stream=true`
- `temperature=0`
- 最大输出 Token：`MODEL_PROBE_MAX_OUTPUT_TOKENS`
- 协议成功：HTTP 2xx，且 SSE 或兼容 JSON 格式有效；
- 语义成功：规范化文本严格为 `ok`。

### 7.2 Responses

- 端点：`POST /v1/responses`
- 固定输入与 Token 上限；
- 协议成功：HTTP 2xx 且 JSON 结构有效；
- 语义成功：`output_text` 或输出内容规范化后为 `ok`。

### 7.3 Embeddings

- 端点：`POST /v1/embeddings`
- 固定输入：`healthcheck`
- 语义成功：至少返回一个非空 embedding 向量；
- 不检查 completion token。

### 7.4 Rerank

- 端点：`POST /v1/rerank`
- 固定 query 和两个固定 documents；
- 语义成功：返回至少一个 result/data 项。

### 7.5 Unsupported

- 不发网络请求；
- 写入 `skipped + unsupported_capability`；
- UI 显示“未适配”，不能显示故障，也不能显示健康。

### 7.6 能力识别

- `MODEL_PROBE_CAPABILITY_MAP` 精确映射优先；
- Embedding、Rerank 使用保守名称识别；
- 图片、音频、TTS、转写等名称默认 unsupported；
- 其他未知模型默认 Chat Completions；如果模型只支持 Responses，运营人员必须提供精确映射。

## 8. 配置契约

| 环境变量 | 默认值 | 硬边界 |
|---|---:|---|
| `MODEL_PROBE_ENABLED` | `false` | 未显式开启不发送请求 |
| `MODEL_PROBE_API_KEY` | 空 | 必须是专用模型 Token，不写日志和 API 响应 |
| `MODEL_PROBE_MODELS` | 空 | 精确逗号白名单；空列表不运行 |
| `MODEL_PROBE_CAPABILITY_MAP` | 空 | `model=capability` 逗号映射 |
| `MODEL_PROBE_INTERVAL_SECONDS` | `300` | 60–86400，否则回到 300 |
| `MODEL_PROBE_TIMEOUT_SECONDS` | `20` | 3–120，否则回到 20 |
| `MODEL_PROBE_STALE_SECONDS` | `900` | 不小于调度周期，最大 7 天 |
| `MODEL_PROBE_MAX_CONCURRENCY` | `2` | 1–10 |
| `MODEL_PROBE_MAX_MODELS_PER_RUN` | `20` | 1–100 |
| `MODEL_PROBE_DAILY_REQUEST_BUDGET` | `500` | 1–100000 |
| `MODEL_PROBE_MAX_OUTPUT_TOKENS` | `4` | 1–32 |
| `MODEL_PROBE_RETENTION_DAYS` | `30` | 1–365 |

配置 API 只返回是否配置、白名单、限制和预算使用量，不返回 API Key。

## 9. Tool Store v9 数据模型

### 9.1 `model_probe_runs`

记录一次计划或手动任务：

- 唯一 `run_key`；
- 请求指纹；
- `scheduled/manual` 触发类型；
- 操作主体；
- running/succeeded/partial/failed/skipped/cancelled 状态；
- 请求、成功、失败、跳过数量；
- 有限错误代码与错误说明；
- 开始、完成、创建、更新时间。

所有计数满足：

```text
attempted_count = success_count + failure_count + skipped_count
attempted_count <= requested_count
```

进程启动时必须以“本进程启动时间”为边界，查找更早开始且仍为 `running` 的遗留任务。恢复逻辑根据已保存的 attempt 重算成功、失败和跳过数量，将任务终态写为 `cancelled`，错误码固定为 `process_restarted`。不得把本进程刚创建的任务误判为遗留任务，也不得让幂等重放永久返回一个不会结束的 `running` 任务。

### 9.2 `model_probe_attempts`

每模型一条脱敏结果：

- run、模型、能力、端点；
- success/failure/skipped；
- protocol success 与 semantic success；
- HTTP 状态；
- 响应头、首字和总延迟；
- 错误分类与截断错误说明；
- 响应 SHA-256；
- 开始、结束、创建时间。

明细禁止 UPDATE；保留任务允许 DELETE 过期遥测。

### 9.3 `model_probe_rollups`

按“小时 + 模型 + 能力”聚合：

- 尝试、成功、失败、跳过数量；
- 延迟累加值和样本数；
- 最近探测时间。

Dashboard 24h 可用率和平均延迟从 rollup 读取；最新结果与诊断历史从有索引的 attempt 查询读取。

## 10. API 任务

### 10.1 状态

```http
GET /api/model-status/probes/status
```

viewer 可读。返回启用状态、配置状态、任务运行状态、调度周期、并发、日预算、今日使用量、保留周期、白名单、下次任务和最近任务。不得返回 Token。

### 10.2 汇总

```http
POST /api/model-status/probes/summary
Content-Type: application/json

{"models":["gpt-5","text-embedding-3-small"]}
```

- viewer 可读；
- 最多 200 个模型；
- 请求体最多 32 KiB；
- 返回每模型最新探测、24h 聚合、状态、来源状态和原因。

### 10.3 手动探测

```http
POST /api/model-status/probes/run
Idempotency-Key: probe-...
Content-Type: application/json

{"models":["gpt-5"]}
```

- 至少 operator；
- 必须提供 8–128 字符幂等键；
- 只接受白名单模型；
- 不超过单次上限和日预算；
- 有任务运行时返回 `409 PROBE_BUSY`；
- 预算不足返回 `429 PROBE_BUDGET_EXCEEDED` 与 `Retry-After`；
- 首次提交返回 202；相同主体、模型集合和幂等键重放返回原任务且不重复请求；
- 相同幂等键不同请求返回 `409 IDEMPOTENCY_CONFLICT`。

### 10.4 历史

```http
GET /api/model-status/probes/history?model=provider%2Fmodel&limit=20
```

- viewer 可读；
- 支持模型名包含 `/`；
- limit 1–100；
- 只返回脱敏遥测。

## 11. 前端任务

### 11.1 页面信息架构

1. 顶部模型可靠性说明和主要操作；
2. 主动探测状态条：配置、预算、调度、并发与保留期；
3. KPI：监控模型、需要关注、双源健康、证据不足；
4. 需要关注列表：异常与降级优先；
5. 紧凑模型表格；
6. 移动端独立卡片行；
7. 右侧诊断抽屉；
8. 独立监控范围选择器。

### 11.2 表格字段

```text
模型 | 综合状态 | 真实流量 | 主动探测 | 探测可用率
首字延迟 | 总延迟 | 最近证据 | 诊断入口
```

### 11.3 交互要求

- 默认按异常、降级、未知、单源健康、双源健康排序；
- 支持模型名称、综合状态、NewAPI token group 和时间窗口筛选；
- 点击任意行打开诊断抽屉；
- 诊断抽屉显示真实流量时间槽、探测摘要、延迟和最近 20 条探测；
- 手动探测按钮根据 disabled/misconfigured/running/budget exhausted 自动禁用；
- 60 秒自动刷新；
- 刷新失败保留已渲染数据并明确展示错误，不把空数组当正常；
- Escape 可以关闭选择器和诊断抽屉；
- 公开嵌入页继续使用原兼容组件。

## 12. 迁移与回滚

### 12.1 升级前

1. 记录当前镜像 digest 与发行 commit；
2. 备份 `.env`；
3. 对实际 `TOOL_STORE_PATH` 使用 SQLite Online Backup；
4. 确认备份可读、权限受控；
5. 检查磁盘空间可容纳新表和 WAL；
6. 默认保持 `MODEL_PROBE_ENABLED=false` 完成首次升级。

### 12.2 首次启动

- Tool Store 从 v8 前向迁移到 v9；
- 迁移失败时进程启动失败关闭；
- Manager 启动后先取消上一次进程遗留的 `running` 任务，再启动周期调度；
- 未启用主动探测时不会产生外部模型请求；
- readiness 必须确认 Tool Store schema 为最新版本。

### 12.3 启用探测

1. 创建专用低权限模型 Token；
2. 设置精确模型白名单；
3. 对非聊天模型设置能力映射；
4. 使用低并发、低日预算开始；
5. 先手动探测 1–2 个低成本模型；
6. 检查 NewAPI 日志、探测结果和计费；
7. 再开启周期调度。

### 12.4 回滚

- 应用镜像可回滚到已验证的旧 digest；
- v0.5.2 不认识 Tool Store v9，不能把镜像回滚等同于数据库自动降级；
- 需要完整回滚时，停止 v0.6.0 后恢复升级前 Tool Store 备份；
- 仅关闭主动探测时可设置 `MODEL_PROBE_ENABLED=false`，无需删除表或遥测；
- 不允许手工修改 `schema_migrations` 或删除迁移对象伪造降级。

## 14. 验收标准

## 15. 发布红线

出现任一情况不得创建正式发行版：

- 非聊天模型被发送到 Chat Completions；
- 主动探测默认开启或白名单为空仍发出请求；
- API Key、Authorization 或原始响应进入持久化；
- 达到预算后仍继续调用；
- 重复幂等请求产生重复探测；
- 进程重启后遗留任务持续显示 `running`，或恢复逻辑误取消当前进程任务；
- stale、empty、unavailable 被显示为健康；
- Tool Store 迁移不可升级或 migration checksum 未固定；
- 前端构建通过但实际页面空白、出现框架错误覆盖层或主要交互不可用；
- main/tag CI 未成功；
- tag 不是 annotated `v0.6.0` 或 tag commit 不在 main；
- 发行镜像无法证明对应发行 commit。
